**Date:** 19-20 September 2026 · **Scope:** API (`apps/api`), web console (`apps/web`), Android app (`intellicash_mobile`) · **Method:** black-box scenarios written independently of the code under test, run against a dedicated QA database and API, then unit/regression tests added for every fix.

A workflow was counted as passing only when the screen (or API response), the database row, the arithmetic, persistence after reload and every dependent screen all agreed.

### Decisions recorded (found, deliberately not changed)

* **Idempotent replay is silent.** Re-sending a ledger entry with the same `clientRequestId` but a different amount returns the *original* entry and moves no money. A hard 409 would jam a phone's whole sync batch on one edited retry. The response shows what was actually recorded.
* **A share-out entry is a legitimate phone-sync type**, so an authorised ledger writer can post one; it re-baselines the share-out cycle (documented behaviour of the offline share-out).
* **No reversal / void for ledger entries** (append-only by design). A mistaken entry needs an offsetting entry; a first-class "correction" workflow is a product decision, not a defect.
* **Over-payment is not refunded automatically at share-out**; it is reported per loan (`overpaidCents`) and is absorbed into the pool. Groups that want refunds need a rule.
* **Maximum single figure is KES 21,474,836.47** (32-bit cents). Enforced with a clear message; widening it needs a schema migration.

## D. Calculation verification (independent)

Every expected figure below was worked out by hand or by the script from its own postings, then compared with the API, the passbook, the reports and the database.

| Topic | Rule verified | Cases |
|---|---|---|
| Savings, social fund, fines | Fund = Σ credits − Σ debits; member totals add up; fines count in "total paid in" | zero, one, many, one cent, two entries by one member |
| Loan interest | Flat monthly on the **original** principal, whole elapsed 30-day months (floor), capped at the term | 29 days → 0; 65 days → 2 months (400.00 on 2,000.00); 200 days capped at 3 months (150.00 on 500.00) |
| Repayments | Oldest loan first; partial; exact; over-payment reported not negative | 400.00 → older owes 250.00, newer still 300.00; 3,000.00 against 2,400.00 → 600.00 over, loan closed |
| Settled loan | Interest stops the day it is paid off | paid 1,200.00 at month 2 → still 0 a month later |
| Loan guards | Loan larger than the fund refused with the shortfall; zero, negative, fractional, text amounts refused | 1 cent over → `INSUFFICIENT_LOAN_FUND` shortfall 1 |
| Welfare | Spend from the social fund; cannot exceed it | one cent over → refused, fund unchanged |
| Share-out | Pool × member shares ÷ all shares (floor, exact), last member takes the remainder; welfare **remainder** split equally; loans netted at principal + interest owed today; cash conserved | payouts sum to the pool; net = payout + welfare − loans; a second request moves nothing |
| Concurrency & retries | Same request id never doubles; 6 parallel identical requests → 1 row; 8 parallel different → 8; 6 parallel 300.00 loans on 1,000.00 → exactly 3 | fund equals Σ ledger (no lost update) |
| Extremes | Largest storable amount accepted; +1 cent refused politely; 1e21 and text refused; 251-entry batch refused whole; a bad entry rolls back the good ones | — |

## E. Authentication and member model — confirmed

1. A **member exists on the server without any login** (name-only members, and members with a phone but no login); money can be recorded for them and the group reads their passbook. *(S2, 11 checks)*
2. A **member with a login is the same record** — creating a login attaches to the existing member row; no duplicate is created; the pre-login history (share bought before the login existed) is visible to the member; a member cannot read another member's passbook; a second login for the same member and a second member on the same phone in a group are refused. *(S3, 10 checks)*
3. **Login first, member later** — self sign-up creates a login with no member; a join request approved against a phone that is already on the roster requires explicit confirmation and attaches to the **existing** member; a person with no roster entry gets exactly one new member; approving twice is refused. *(S4, 11 checks)*
4. **Removing a login never removes the member** — suspending blocks sign-in with a clear reason; closing strips the login's identity and detaches it while the member row, every transaction and the group's view are unchanged; the old session dies; a fresh login can be created for the same member and reads the same history; still one member row. *(S5, 12 checks)*

## F. Backend verification

* Every UI/API-created record in scenarios 1–4 was re-read from the database (member, membership link, ledger row, loan row, fund balance) and compared, not only echoed back.
* Fund balance = Σ ledger entries after every concurrent scenario.
* Permissions matrix: 200 role × operation × scope cells match the role table; 404 (not 403) is returned for a group that is not yours; anonymous and forged sessions get 401.

## H. Phone app (Android) — screen-by-screen on the emulator

Method: build of the app against the QA API, driven through adb (real taps and typing), each screen read from the accessibility tree and from a screenshot, every record then checked in the QA database. Offline behaviour was tested with the phone's network switched off and on, with the **server stopped and restarted**, and with a forced restart.

## J. The open issues, fixed (20-21 September 2026)

### J-1. A share-out done on the phone reaches the online record (R-1)

**What was wrong.** The phone worked out and paid a share-out correctly, kept the payouts, and started a new cycle - but the payout rows went into a queue that nothing drained. The console kept saying "Cycle 1", its funds still held the money, member statements online still showed the old savings, and "Sync & Backup" said everything was backed up.

**The decision.** The console also offers a server-side "reviewed" share-out that works the payouts out from the server's books. The two cannot both be authoritative. The phone's share-out is money that has *already been counted out at the table*, so the server is told what was paid rather than asked to work it out again (recomputing would quietly change what members were paid whenever the two disagreed). The console's own share-out stays as it was, and the two are made unable to pay a cycle twice.

**Server** (`POST /groups/:groupId/share-outs`, `services/share-out-record-service.ts`). One transaction records each loan settlement (`LOAN_REPAYMENT`), each payout (`SHARE_OUT_PAYOUT`) and the welfare split (`WELFARE_SHARE_OUT`), then closes the cycle. Money coming in is posted before money going out so the loan fund is never overdrawn part-way. It refuses, and leaves **nothing** behind (every refusal is tested against the ledger, both funds and the cycle):

| Refused because | Code |
|---|---|
| the server has already closed that cycle (the console shared it out) - sending would pay members twice | `SHARE_OUT_CYCLE_CLOSED` |
| an earlier cycle has not arrived yet | `SHARE_OUT_CYCLE_AHEAD` |
| the server's share purchases for the cycle are not the phone's (named per member) - overridable only by a person, with `force` | `SHARE_OUT_OUT_OF_STEP` |
| the loan fund cannot cover it (some of the cycle has not arrived) | `SHARE_OUT_FUND_SHORT` |
| a figure does not add up, or a member appears twice or is not in the group | `SHARE_OUT_ARITHMETIC`, `SHARE_OUT_DUPLICATE_MEMBER`, `MEMBER_NOT_FOUND` |
| a meeting is open on the console | `CYCLE_HAS_OPEN_MEETINGS` |
| the account may not end a cycle (a village agent) - same rule as the console's Close cycle | `FORBIDDEN` |

A retry after a lost reply is recognised by the id the phone gave the share-out, kept on the cycle it closed (`Cycle.closedByShareOutId`, unique per group) and answered with what was already recorded, `200` instead of `201`, writing nothing.

**Phone.** `ShareOutSyncService` sends one share-out; `AutoSyncCoordinator` does the ordering, because the server files every record under the cycle open *when it arrives*: a cycle's meetings first, then its share-out, then the next cycle's meetings. A meeting that has not gone up holds the share-out back, and a refused share-out holds back what follows it - all of it still counts as waiting and goes when what is in front of it does. A share-out refused for a reason a person can act on shows on the share-out screen in the server's words with **Send now**, and **Send anyway** (after a confirmation) only for the share-purchase difference. A cycle the server had already closed is marked "already shared out online" and stops holding anything up. A meeting still open now blocks a share-out ("Close Meeting #N first") so a meeting's savings cannot straddle the line. Phones already in the field have share-outs that were never sent: the schema upgrade (v11) marks those handled, so they are neither sent nor able to hold up the meetings after them.

### J-2. A new phone gets the group's whole history (R-2)

**What was wrong.** A treasurer who changed phone got the roster and the settings; balances are worked out from the rows on the phone, so a phone with none of the rows reported a group with no money - and would have worked a share-out out from that.

**The fix.** `GET /groups/:groupId/restore-bundle` (group's own account or platform admin only) returns, in one consistent snapshot, the cycles, meetings, attendance, every ledger entry (with its cycle and the loan a repayment paid), the loans and the rules the group set. `GroupHistoryImporter` writes it in **one local transaction**: meetings numbered in order and recorded as already backed up (so none is ever sent back), share purchases (exact amount kept, never rounded to a share), the social fund, fines, loans with their repayments, past share-outs for closed cycles, and the open cycle's start - so this cycle's balances read as they did on the old phone. If the group had been shared out on the console without closing the cycle, balances start after that payout, as the server counts them. If the signal drops, the group is still loaded and the history follows at the next sync; it never goes underneath meetings the new phone has already recorded (they would share numbers).

What does **not** come across, and why: online records tied to no meeting or to a member the phone does not have (counted and reported, not guessed); welfare expenses (already mirrored by the welfare sync); the loan multiplier and the social-fund amount per meeting (they exist only on the phone, so a restored group has 3x and 0 until the treasurer sets them).

### J-3. A book is no longer linked to a group on a guess (R-6)

Same name (ignoring case and spacing): links itself, as before. Different name but an empty server group: previously linked silently - and sent the book's members and money into whatever group that was. Now the dashboard shows a card with both names, **Link them** / **Not now**; "Not now" is remembered. Names differing with a server group that already has records: never offered. The stronger M-30 guard (a book linked to another group) is unchanged.

### J-4. New groups start on the platform's loan model (R-7)
