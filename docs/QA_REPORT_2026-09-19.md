**Date:** 19 September 2026 · **Scope:** API (`apps/api`), web console (`apps/web`), Android app (`intellicash_mobile`) · **Method:** black-box scenarios written independently of the code under test, run against a dedicated QA database and API, then unit/regression tests added for every fix.

A workflow was counted as passing only when the screen (or API response), the database row, the arithmetic, persistence after reload and every dependent screen all agreed.

### Decisions recorded (found, deliberately not changed)

* **Idempotent replay is silent.** Re-sending a ledger entry with the same `clientRequestId` but a different amount returns the *original* entry and moves no money. A hard 409 would jam a phone's whole sync batch on one edited retry. The response shows what was actually recorded.
* **A share-out entry is a legitimate phone-sync type**, so an authorised ledger writer can post one; it re-baselines the share-out cycle (documented behaviour of the offline share-out).
* **No reversal / void for ledger entries** (append-only by design). A mistaken entry needs an offsetting entry; a first-class "correction" workflow is a product decision, not a defect.
* **Over-payment is not refunded automatically at share-out**; it is reported per loan (`overpaidCents`) and is absorbed into the pool. Groups that want refunds need a rule.
* **Maximum single figure is KES 21,474,836.47** (32-bit cents). Enforced with a clear message; widening it needs a schema migration.

## D. Calculation verification (independent)

Every expected figure below was worked out by hand or by the script from its own postings, then compared with the API, the passbook, the reports and the database.

| Topic | Rule verified | Cases |
|---|---|---|
| Savings, social fund, fines | Fund = Σ credits − Σ debits; member totals add up; fines count in "total paid in" | zero, one, many, one cent, two entries by one member |
| Loan interest | Flat monthly on the **original** principal, whole elapsed 30-day months (floor), capped at the term | 29 days → 0; 65 days → 2 months (400.00 on 2,000.00); 200 days capped at 3 months (150.00 on 500.00) |
| Repayments | Oldest loan first; partial; exact; over-payment reported not negative | 400.00 → older owes 250.00, newer still 300.00; 3,000.00 against 2,400.00 → 600.00 over, loan closed |
| Settled loan | Interest stops the day it is paid off | paid 1,200.00 at month 2 → still 0 a month later |
| Loan guards | Loan larger than the fund refused with the shortfall; zero, negative, fractional, text amounts refused | 1 cent over → `INSUFFICIENT_LOAN_FUND` shortfall 1 |
| Welfare | Spend from the social fund; cannot exceed it | one cent over → refused, fund unchanged |
| Share-out | Pool × member shares ÷ all shares (floor, exact), last member takes the remainder; welfare **remainder** split equally; loans netted at principal + interest owed today; cash conserved | payouts sum to the pool; net = payout + welfare − loans; a second request moves nothing |
| Concurrency & retries | Same request id never doubles; 6 parallel identical requests → 1 row; 8 parallel different → 8; 6 parallel 300.00 loans on 1,000.00 → exactly 3 | fund equals Σ ledger (no lost update) |
| Extremes | Largest storable amount accepted; +1 cent refused politely; 1e21 and text refused; 251-entry batch refused whole; a bad entry rolls back the good ones | — |

## E. Authentication and member model — confirmed

1. A **member exists on the server without any login** (name-only members, and members with a phone but no login); money can be recorded for them and the group reads their passbook. *(S2, 11 checks)*
2. A **member with a login is the same record** — creating a login attaches to the existing member row; no duplicate is created; the pre-login history (share bought before the login existed) is visible to the member; a member cannot read another member's passbook; a second login for the same member and a second member on the same phone in a group are refused. *(S3, 10 checks)*
3. **Login first, member later** — self sign-up creates a login with no member; a join request approved against a phone that is already on the roster requires explicit confirmation and attaches to the **existing** member; a person with no roster entry gets exactly one new member; approving twice is refused. *(S4, 11 checks)*
4. **Removing a login never removes the member** — suspending blocks sign-in with a clear reason; closing strips the login's identity and detaches it while the member row, every transaction and the group's view are unchanged; the old session dies; a fresh login can be created for the same member and reads the same history; still one member row. *(S5, 12 checks)*

## F. Backend verification

* Every UI/API-created record in scenarios 1–4 was re-read from the database (member, membership link, ledger row, loan row, fund balance) and compared, not only echoed back.
* Fund balance = Σ ledger entries after every concurrent scenario.
* Permissions matrix: 200 role × operation × scope cells match the role table; 404 (not 403) is returned for a group that is not yours; anonymous and forged sessions get 401.
